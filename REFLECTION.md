## 1. Who are your users, and what changes for them?
The user of LastBatch is a bakery store manager working the closing shift at a small chain of around forty neighbourhood shops. This is an internal user whose existing work is being augmented: the manager is responsible for the fresh-food markdown and waste decision at the end of each trading day. At around 5 PM, the manager currently walks the shelves and decides from memory whether each unsold item should receive a 20% discount, a 50% discount, or be pulled. There is no record of those decisions or their cost.
LastBatch changes this by replacing the memory-based shelf walk with a structured closing list. Items are ordered by bake time, the manager makes one of three decisions for each item, and an undecided counter shows when the job is complete. The second screen then turns those decisions into a seven-day view of markdowns, pulls and money lost, giving the manager an input for deciding what to bake less of. The product therefore does not replace the manager's judgment; it structures and records it.

## 2. How did AI increase AND limit your abilities?
AI significantly increased my capacity because I am not a programmer. My main contribution was defining the business problem, user, workflow and constraints, while Google AI Studio translated that specification into a working React application with two screens. This allowed me to spend more time evaluating whether the product made sense rather than manually building the interface.
At the same time, AI exposed a limitation in my own ability to specify and inspect technical systems. My master prompt explicitly prohibited Gemini API calls, @google/genai, API-key handling and outside services. However, the generated repository initially contained an .env.example with GEMINI_API_KEY documentation and a Gemini dependency even though the application made no model calls. I only discovered this when I deliberately searched the repository beyond the application code. I subsequently removed those leftovers.
This showed me that a guardrail is only as strong as my understanding of what needs to be guarded. As a non-programmer, I can state what I do not want, but I may not yet know every technical place where an unwanted capability can appear.

## 3. Where did YOU exercise judgment?
I was primarily in the loop. AI generated the implementation, but I decided whether the output matched the product and whether its data made business sense.
One important judgment moment was the date problem on the “This week” screen. The first version showed “Sunday (Yesterday) · Sep 6”, even though yesterday was Monday, 7 September. I asked AI to relabel the seven days ending yesterday and remove the relative “Yesterday” wording so the interface would not become stale. This was not simply a coding correction: I recognised that a technically valid label could still be wrong for the actual user.
The more important judgment moment came when I checked the numbers. The weekly screen initially implied 77 pulls across seven days for a shop represented by only 14 current products, while the closing list suggested that most items would be marked down rather than pulled. I asked AI to reduce daily pulls to 1–4 and update the totals and “Bake Less of These” list consistently. I then independently re-added the daily figures and verified that they totalled 18 pulls and $215.00.
I was technically in the loop but contributed little when I first checked the preview against my numbered requirements. The individual screens appeared to work, so I accepted the output too quickly. The lesson was that approving whether features exist is different from judging whether the whole system is coherent.

## 4. What did AI build that you never asked for?
The first version added several elements that were never part of my specification: a shop identity, progress bar, second counter, toast notifications and a colour scheme. It also calculated the discounted price for each markdown button, which I had not requested but which I considered useful because a manager needs the actual price when making a shelf decision.
More importantly, the build exposed something that I had never specified: that the two screens had to describe the same shop and the same underlying reality. The first version's weekly data was inconsistent with the closing list, producing an implausibly high number of pulls. This was not an extra feature added by AI; it was a gap in my own requirements that AI did not know to protect against.
I noticed it after checking the deployed application. I could have caught it earlier by writing cross-screen acceptance criteria, not just screen-by-screen requirements. For example, I should have explicitly required the weekly totals to reconcile with the underlying closing decisions.

## 5. What does this teach organisations?
First, organisations should treat human verification as part of AI-assisted development, not as a final formality. My 77-pull example shows that an output can be technically valid but operationally unreasonable. Someone who understands the business context still needs to challenge the result.
Second, organisations should make scope and acceptance criteria explicit before asking AI to build. AI added several unrequested interface elements, and my specification did not state that the two screens had to reconcile. Better guardrails would have reduced both forms of drift.
Third, organisations should require source-level verification, not just preview-level verification. In my project, the live preview could look correct while the repository still contained unnecessary Gemini/API-related configuration, and later the deployed site continued showing old numbers because the updated source had not actually reached the repository. Checking the source files and repository state was therefore part of verifying the product, not merely a technical housekeeping task.
Overall, the project showed me that AI can greatly increase execution capacity, but it does not remove the need for human judgment. The most important work was deciding what the output should mean, noticing when it did not make sense, and verifying that the generated system matched the intended business problem.
